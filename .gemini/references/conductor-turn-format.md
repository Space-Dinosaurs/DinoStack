# Conductor Turn Format

## Purpose

The conductor's default output is noise. Every operator turn read is attention spent; a status-only turn spends that attention for no return, and an unstructured turn forces the operator to rebuild context on every check-in - a cost multiplied across many concurrent sessions. This file exists to guard that attention. North Star pillar 1 states the requirement directly (`docs/overview/vision.md:16`):

> "Guard operator attention. Surface decisions and work-stoppages, not status."

Two mechanisms enforce this mechanically: a warrant-bound shape for any turn that IS written (Rule A, §4), and an emission gate that decides whether a turn should be written at all (Rule B, §2). A third axis governs a defect spotted mid-task, before either question is reached - see Self-discovered defects, below - and is deliberately prose-only, not mechanized; its own disposition statement explains why. Neither Rule A nor Rule B replaces judgment - both are the mechanical form of the same North Star sentence.

**DS-156 note.** An earlier version of Rule A added a structured block to every turn without removing the surrounding prose - structure was added, nothing was subtracted, and the net effect was a *bigger* turn to read, the exact regression pillar 1 forbids. §4 below fixes this by binding shape to which warrant fired: an execution turn (Decision/Stoppage/Completion, no Answer) is the structured block and nothing else; an Answer turn is prose and nothing else. The two shapes never mix except at the very end, where `## Operator decisions` may still close either one.

## The four warrants (Rule B)

A conductor turn is warranted only when at least one of these four conditions holds. Each has a one-line test:

1. **Decision** - a `## Operator decisions` heading is present in the turn.
2. **Stoppage** - a `Waiting:` line is present in the turn (see §7, forced yield).
3. **Completion** - the turn contains `[phase: complete]`, an explicit terminal-completion phrase anywhere in the turn (including the Conductor template's own `State: complete` field), OR (DS-156) the turn's identity line ITSELF opens with a short terminal declaration - "Done.", "Verification complete.", "Both PRs are done and verified.", "Merged and fully cleaned up.". **A conductor turn never carries `Status: DONE`** - that string is the engineer-role return contract's terminal enum value (`content/agents/engineer.md`), and its only possible appearance in a conductor turn is a RELAY of a subagent's return text ("The engineer returned Status: DONE, spawning the Skeptic now.") - a still-in-progress turn the guard must keep flagging, not a warrant of its own; `hooks/enforce-turn-shape.py` deliberately does not treat that string as a completion signal. A bare `done`, `shipped`, or `merged` occurring MID-MESSAGE (not on the identity line) still does **not** count - those words commonly appear in ordinary status prose ("unit 2 merged", "PR merged, pulling main") and are too weak a signal on their own to carry the completion warrant. A completion claim is further VETOED outright when a continuing-work signal is present anywhere in the turn - a non-empty `Running:` field, or a phrase such as "one to go", "remaining after", "is/are still running", bold-wrapped `**In progress**` in any position (not restricted to a sub-heading), "review(s) running", or "running on" - closing the shape where the completion declaration is genuinely sentence-complete on the identity line but the body separately says the dependent work is still in flight ("Security audit complete." ... "Skeptic is still running."). DS-157 round 1 added four phrases here ("in progress", "review(s) running", "running on", "still open"); DS-157 round 2 dropped "still open" and narrowed "in progress" to the bold-wrapped `**in progress**` shape after a full-corpus measurement found the bare forms firing on tracker-status vocabulary describing OTHER work, not this turn's own - before DS-171 retired `_status_only_flag`, this same regex was also shared with that check's advisory-suppression logic, so an over-broad addition here would have silently vetoed real completions on both the blocking-adjacent warrant path and the advisory one; today `_status_only_flag` is restored and BLOCKING (DS-ANSWERFIRST) but shares NO suppression logic with this regex - its two suppressors are the transcript-position predicate and the prose recall, neither of which consults completion vocabulary - so only the blocking-adjacent warrant path is affected. See `hooks/enforce-turn-shape.py`'s `_CONTINUING_WORK_PHRASE_RE` docstring for the phrase-by-phrase measurement. See §10's hook-contract entry for the corpus measurement (main-agent population only - this hook never evaluates subagent/sidechain turns) behind both the identity-line restriction and the continuing-work veto. **DS-157: this warrant is deliberately NOT widened to recognize a completion declaration that opens the turn's first body paragraph rather than the identity line itself** ("Both units shipped.\n\n**DS-156 is done.** ..." - the identity line alone does not match, since "shipped" has no trailing completion-adjacent word before the period). Granting the warrant for that shape would route the turn onto the BLOCKING `_execution_prose_flag` general branch (§4), which only permits `State:`/`Running:`/`Blocked:`/`Waiting:` slot lines - every measured real instance of this shape is a multi-paragraph prose report with narrative bullets, which that branch would BLOCK outright. Before DS-171, `§9`'s now-deleted `_status_only_flag` recognized this shape directly (`_has_body_completion_declaration`) and suppressed its own advisory only, never granting this warrant - see §9's hook-contract entry for the corpus measurement and the residual gap this left (a completion declared past the first body paragraph). DS-171 deleted `_status_only_flag` outright, and DS-ANSWERFIRST restored it WITHOUT that shape-specific suppression logic (`_has_body_completion_declaration` stays deleted - it was a phrase-shaped helper of exactly the class Pillar 8 names a smell), so this hook still runs no suppression for this shape specifically. A completion report of this shape therefore now BLOCKS: that is the disclosed residual false positive recorded in §9's `_status_only_flag` hook-contract bullet, not an unnoticed gap. The status-only rule's always-loaded carrier is the kernel paragraph in `content/sections/02-delegation.md`, which reaches every harness (see §5).
4. **Answer** - the turn contains a quoted fragment responding to the operator's immediately-preceding message, OR (DS-155) the operator's most recent genuine message looks like a direct question AND is still the IMMEDIATELY preceding turn boundary - no genuinely separate, earlier completed assistant turn since it was asked. A stale question (several later background-agent check-in turns have happened since) grants nothing; see §10 for the corpus-measured fix to this recency check (it correctly ignores the model's own earlier narration-then-tool-call steps within the SAME turn, while still catching a genuinely stale-by-one question). This is the weakest of the four and best-effort only; it exists so a direct question never goes unanswered, not as a loophole for narration.

Everything else - agent spawned, agent returned, phase advanced, unit merged, CI green - is a silent continue. No turn is written for it.

## Scope filter

A conductor turn reports on **this session's work only**. Do not mention other concurrent sessions, other tickets, or unrelated in-flight work - the operator is tracking those elsewhere and a cross-session mention adds cost without adding a decision. Do not include rationale unless a decision surfaced in the *same* turn depends on it; rationale for past decisions belongs in the PR body, the plan artifact, or a memory file (see §5, bullet 3).

## Self-discovered defects

This is a THIRD axis, distinct from both mechanisms in §1: Rule A governs the shape of a turn that gets written, Rule B governs whether a turn gets written at all, and this rule governs what happens to a defect you notice yourself mid-task, before either question is reached. A defect you discover while doing the work is not a report item - it is work, under normal risk classification, in the same turn.

**"Fix it" means dispatching it to an engineer, not editing it in the conductor's own turn.** The conductor never edits shippable artifacts directly, including Trivial one-line changes - that floor covers a small self-discovered defect, it does not exempt one (`content/rules/conventions.md` §Git Workflow, and the delegation floor referenced throughout this methodology). "In the same turn" means: spawn the Worker now, instead of naming the issue and moving on - not that the conductor makes the edit itself.

Proportionality ("too small to be worth a cycle") is not a valid reason to defer. If the fix is small enough to describe, it is small enough to dispatch - describing it costs the operator more attention than spawning the fix costs you. A follow-up ticket, or any other handoff that leaves the defect unresolved for later (a PR comment, "noted in #N", a mention to circle back to), is the same defect with extra steps when the fix is dispatchable right now.

The only legitimate reasons to leave an issue unfixed are the ones that already stop work elsewhere in this methodology: it is genuinely out of scope for the task at hand, it requires an operator decision, or it is structurally blocked. Name which one. **When in doubt, dispatch the fix** - proportionality is not a fourth exemption, and the default is to act, not to name the issue and leave it. "Easy to lose track of" is not one of the three.

**This rule is deliberately prose-only and unmechanized**, the same disposition the warrant rule's instances get: no mechanical check can tell a genuinely out-of-scope defect from a deferred one, or confirm that "dispatched to an engineer" actually happened, without re-running the delegation floor's own judgment call. Enforcement here is review, not a hook.

**Forbidden turn-ending shape: naming a spotted issue you chose not to fix, absent one of those three reasons.**

```
REJECTED: "One loose end I deliberately left: X isn't listed in the manifest.
Genuinely minor, but it's the kind of thing that's easy to lose track of
once the session closes."
```

**CORRECT behavior:** dispatch the fix to an engineer in the same turn. When the turn reporting it is itself an execution turn (§4), fold the resolution into a status slot rather than adding narrative prose beside it - the same idiom §10's residual-false-positive list uses for a `Waiting:` line ("fold the reason into the line itself"):

```
DS-123 · fix/foo · [phase: skeptic-review]
State: added X to the manifest
```

## Warrant-bound shape (Rule A)

Which of the four warrants fired (§2) determines the turn's shape, not just whether a turn happens at all. Bind on the Answer warrant first: **Answer always wins the shape question**, regardless of what else co-fires. A turn carrying the Answer warrant is an **Answer turn**, even if a Decision, Stoppage, or Completion warrant also fired on the same turn. A turn with no Answer warrant but at least one of Decision/Stoppage/Completion present is an **execution turn**. A turn with none of the four warrants present is neither shape: per Rule B (§2) it should not have been written at all. §9's hook contract routes it to `_status_only_flag` rather than to either shape check - DS-171 retired that check, and DS-ANSWERFIRST restored it as a BLOCKING one, so this branch is again the only place a zero-warrant turn is mechanically caught. See §9's classification-order bullet for the full three-way gate and §9's `_status_only_flag` bullet for its three-condition gate.

### Execution turns

An execution turn (Answer warrant ABSENT, at least one of Decision/Stoppage/Completion PRESENT) follows this fixed order, and **the structured block IS the entire turn - zero prose**:

1. **Identity line first**: `ticket · branch · [phase: x]`. The `[phase: label]` breadcrumb itself is governed by `content/references/subagent-protocol.md` Rule 6 - read it there for firing points and the crash-recovery rationale; it is not restated here to avoid two copies drifting. **This is a documented CONVENTION, not a mechanically-enforced one (DS-155 round 3).** `hooks/enforce-turn-shape.py` no longer flags a missing or malformed identity line - see §10's history note for why the mechanical check was removed rather than repaired a third time. Following it remains expected practice; nothing on this repo's Stop-hook path will tell the conductor when it does not.
2. **Status slots**: `State`, `Running`, `Blocked` - one line each, omitted when empty. Capped at **1-3 status lines per turn**, with the forced-yield shape (§7) as the sole exception to the cap itself, not merely to its line contents: a forced-yield turn drops `State`/`Running`/`Blocked` entirely and instead carries one `Waiting:` line per agent, however many that is - the count is unbounded, not re-capped at 1-3.
3. **`## Operator decisions`, last.** Placement and internal formatting are governed by `content/sections/02-delegation.md` - read it there rather than here. When present, it terminates the turn: nothing follows it.

**The status region is every non-blank, unfenced line after the identity line and before `## Operator decisions` (or before end-of-message when no decisions heading is present)** - the block governed by step 2 above (`State`/`Running`/`Blocked`) plus any `Waiting:` lines. This is the same region `hooks/enforce-turn-shape.py` computes via `_segment`/`_regions`; a trailing pre-heading aside sits INSIDE it, not outside.

**"One line" understates how much content a single physical line can hold: markdown soft-wraps, so one line routinely renders as a full paragraph, not a short sentence.** Before DS-156 this file described the gap as "a full narrative sentence" at position 1, which itself understated the same margin - a single unbroken line can carry many sentences with no line break at all. `STATUS_LINE_MAX_CHARS` (below) is the fix for this specific margin: it bounds physical-line CONTENT LENGTH, not visual line count, so a soft-wrapped 200-character line is now caught the same way a hard-wrapped one would be.

**The identity line itself is exempt from SHAPE validation by construction, not by rule, but it is NOT exempt from the LENGTH bound below (DS-156, contract).** `_segment` takes the first non-blank line, whatever its content, to BE the identity line, and the status region starts strictly after it. Because the identity line never enters the status region, it was previously invisible to `_execution_prose_flag` in every respect - shape AND length. `STATUS_LINE_MAX_CHARS` (defined below, in exactly one place) closes the length half of that gap: a position-1 line exceeding it is flagged **on every execution-turn branch, not only the general branch** - the bound is a property of position 1 itself, not of which branch (§9) is running, so a sole-stoppage/forced-yield turn cannot evade it by using its wider raw-line domain to smuggle an over-length line into position 1. (Markup-blindspot fix: the finding this produces can now downgrade to ADVISORY when the identity line itself demonstrably clears the same answer-shaped-prose evidentiary standard used elsewhere in this hook - see §9's hook-contract bullet - but the line is still always FLAGGED at this length; only its severity is conditional.) The line's SHAPE (whether it looks like `ticket · branch · [phase: x]`) is still never checked, on either branch. A length bound is not a shape predicate - it does not reopen DS-155's rejected identity-line shape check (`_session_has_established_identity` / `_session_has_active_ticket_context`, both deleted; see §10's history note), it only denies an unboundedly long line at position 1 the ability to evade every check downstream of it. See the Known uncovered shapes table below (row: single-line preamble) for what remains open after this bound (a short, well-formed-length line at position 1 can still say anything).

**`STATUS_LINE_MAX_CHARS = 200` (DS-156) is defined exactly once, here - every other reference to it in this file, including §9's hook-contract bullets, points back to this paragraph rather than re-asserting its own scope.** It bounds two distinct things: the identity line at position 1, on BOTH the sole-stoppage and the general branch of the `_execution_prose_flag` check (position 1 is checked the same way regardless of which branch owns the rest of the turn); and a `State:`/`Running:`/`Blocked:` slot line, which exists only in the general branch's status region (the sole-stoppage branch permits no slot lines at all - see below). A slot line, or the identity line, exceeding 200 characters is itself a shape violation under `_execution_prose_flag`, the same finding class as an unrecognized label. 200 is chosen to be generous for a genuine status line - well past what a single sentence needs - while still failing a multi-sentence narration: the DS-156 note in the Purpose section above (§1, ~94 words / ~570 characters of normative prose describing the earlier defect, not a quoted turn example) illustrates a narration comfortably past 500 characters. This is a NEW constraint on a NEW check (the general-branch structural shape check, which did not exist as a blocking check before DS-156), not a retroactive import of an existing bound onto unrelated behavior: `Waiting:` lines remain deliberately UNBOUNDED in length in the shape check (see the next paragraph) - round 2 of DS-156 (recorded in the paragraph below) established that importing a length bound onto `Waiting:` lines would convert what is today a silent pass into a block on the hook's only forced-yield path, a behavior change nobody has authorized. `STATUS_LINE_MAX_CHARS` is scoped exclusively to `State:`/`Running:`/`Blocked:` slot lines and the identity line; it does not touch `Waiting:` lines, fenced content, or `## Operator decisions` items, each of which is governed by its own, separately-justified rule elsewhere in this file.

**`SLOT_LINE_MAX_COUNT = 3` (DS-ANSWERFIRST) is likewise defined exactly once, here, and is the sibling of `STATUS_LINE_MAX_CHARS` on the other axis: that constant bounds how LONG one slot line may be, this one bounds how MANY there may be.** It is the mechanical form of the "capped at 1-3 status lines per turn" rule stated in step 2 above, which between DS-171's retirement of the turn-charge volume model and DS-ANSWERFIRST was bounded by nothing at all - a turn could carry twenty well-formed, individually-compliant `State:` lines and pass every check. Two distinct violations share the bound, both **BLOCKING with no downgrade path** (each is a pure count over an already-recognized fixed label set, with no prose content that could be answer-shaped): more than three recognized slot lines in the status region, and two slot lines sharing a label. The duplicate-label half is not redundant with the count half - `State:` twice is structurally not the format ("one line each, omitted when empty") however few lines the turn has. **Scoped to the general branch ONLY.** The sole-stoppage branch's `Waiting:` count stays deliberately UNBOUNDED, per §7's forced-yield exception - one `Waiting:` line per agent, however many that is - and `SLOT_LINE_MAX_COUNT` never reaches that branch. Three is the number of NAMED slots the format defines, one line each; it is not a tunable budget. This is NOT a revival of the retired `_turn_charge`/`_volume_flag` model: there is no whole-message charge, no free pools, and no `BASE_BODY_BUDGET` - it counts recognized slot lines, on one branch. **Pillar 8 obligation, both halves.** *Named catch:* between DS-171's retirement of the turn-charge volume model and DS-ANSWERFIRST, NOTHING bounded the slot-line count - a turn could carry twenty well-formed, individually-compliant `State:` lines and pass every check, against a prose rule that says 1-3. *Retirement condition:* this bound retires TOGETHER WITH `STATUS_LINE_MAX_CHARS`, when the `State:`/`Running:`/`Blocked:` slot vocabulary is replaced by a structured field the harness renders rather than labelled prose lines; at that point both the count and the length axis become schema properties and enforcing them here would be duplicate machinery. Neither is a permanent floor - both are shape checks over a specific textual convention and retire with it.

**Every non-blank, unfenced line in the status region of an execution turn must be a `State:`/`Running:`/`Blocked:` slot line no longer than `STATUS_LINE_MAX_CHARS` (defined above), or a `Waiting:` line matching the shape check's own test - a `waiting` label, a colon, then non-whitespace content, with NO character-length test on `Waiting:` lines in the shape check itself.**

**The sole-stoppage case is a DIFFERENT, WIDER domain, not a narrower whitelist over the same lines** (DS-158 widened it further - see below): when `stoppage` is the SOLE warrant present (no decision, completion, or answer also fired on the same turn), the check inspects every non-blank RAW line after the identity line, fenced or not - the same domain `_forced_yield_flag` inspects today via `_body_after_identity_line`. A `Waiting:` line matching the shape above, or (DS-158) a well-formed `State:`/`Running:`/`Blocked:` slot line within `STATUS_LINE_MAX_CHARS`, is permitted there; any other content, whether fenced or unfenced, is itself a shape violation. **DS-158: prior to this fix, a sole-stoppage turn permitted ONLY `Waiting:` lines - "here is my status and here is what I'm blocked on" (a `Waiting:` line alongside well-formed `State:`/`Running:`/`Blocked:` lines) was a confirmed false positive, blocking legitimate conductor output that mixed the two.** This wider, fence-blind domain remains deliberate on the fenced-content axis: it preserves §7's forced-yield requirement (DS-122's founding rule) exactly as `_forced_yield_flag` enforced it, rather than narrowing to the fence-aware status region and silently opening a bypass for fenced content on a sole-stoppage turn. The identity line at position 1 sits BEFORE this raw-line domain, not inside it, and is covered by the shared `STATUS_LINE_MAX_CHARS` bound defined above regardless: a sole-stoppage turn's `Waiting:` lines stay length-unbounded exactly as before, but the identity line preceding them does not.

**The 120-character bound (`WAITING_LINE_MAX_CHARS`, named in §7) is NOT part of either shape check above.** Before DS-171 it governed free-of-charge status in the ADVISORY turn-charge volume check only (§9); that check is now retired along with `WAITING_LINE_MAX_CHARS` itself and its free-pool table - see §9's Volume check bullet. A `Waiting:` line longer than 120 characters still satisfies both shape checks and never blocks; the length bound no longer has any hook-level consequence at all, only the length-discipline rule this file states (§5, now carried by the `dinostack` output style for Claude Code and by this file's prose for every harness). This remains a deliberate choice, not an oversight: converting a silent pass into a hard block would be a behavior change on a legitimately long agent descriptor, which nobody has authorized.

On the general (non-sole-stoppage) execution-turn whitelist, anything other than a recognized slot line within `STATUS_LINE_MAX_CHARS` and within `SLOT_LINE_MAX_COUNT` (DS-ANSWERFIRST - both the count and the duplicate-label axis, defined above; a fourth slot line or a repeated label BLOCKS with no downgrade path even when every line is individually well-formed), or a shape-matching `Waiting:` line - a narrative sentence, a caveat, a "meanwhile" aside, a restated rationale, or an over-length slot/identity line - is a shape violation, regardless of which execution warrant(s) fired, and BLOCKS by default. **DS-158 exception: unrecognized lines are grouped into CONTIGUOUS blocks - a recognized slot/`Waiting:` line, or a fence boundary, breaks contiguity - and each block is classified INDEPENDENTLY.** Each block must independently clear an average-words-per-unit threshold of `_ANSWER_PROSE_AVG_WORDS_PER_SENTENCE` (8) per `hooks/enforce-turn-shape.py`'s `_is_answer_shaped_prose` - this is the axis a narrative-creep sprawl launders through (many short pings average low), so it stays load-bearing PER BLOCK, unchanged by DS-159 below. **Per-block classification on this average axis is load-bearing, not cosmetic (DS-158 round 2, Skeptic Major 1): a single developed paragraph anywhere in the status region must never downgrade an unrelated, non-adjacent narrative-creep sprawl riding alongside it** - the fix classifies each contiguous run of unrecognized lines on its own merits and blocks the whole finding if any one run fails the average, closing that laundering path. The finding downgrades to ADVISORY only when EVERY block clears that average AND the SUM of units across all such blocks (a sentence, or one bullet/numbered list item regardless of terminal punctuation) reaches `_ANSWER_PROSE_MIN_SENTENCES` (2) - see `_execution_prose_flag`'s own DS-159 comment for the exact aggregation. **DS-159: this unit-count floor is a WHOLE-TURN AGGREGATE, not a per-block requirement, as of this fix** - a real multi-paragraph conductor answer, in this repo's own mandated terse style, routinely produces several genuinely single-sentence, blank-line-separated paragraphs, and requiring 2+ units INSIDE EVERY block blocked the whole turn over one well-formed single-sentence paragraph (reported live at DS-158 round 4 HEAD, `fadfcbf6`; see `ds159-a`/`ds159-b` in `hooks/tests/test-enforce-turn-shape.py` for the pinned shapes). This narrows, but does not remove, the blocking default: a single isolated sentence with NO other answer-shaped block in the turn (the operator's founding complaint, §1's DS-156 note, ds156-e) still blocks, because it is the turn's ONLY block and alone never reaches the aggregate floor of 2. This is the structural predicate `_execution_prose_flag` mechanizes; see §9.

**The 1-3 line cap applies to the status slots only.** `## Operator decisions`, when present, is **additional** to that cap, not counted against it. This is a deliberate asymmetry, not an oversight: the kernel paragraph in `content/sections/02-delegation.md` that governs the Operator decisions block mandates a multi-line format per decision item - "the recommended action, one line of why, and the reversal offer" - and explicitly forbids imposing a numeric cap on the number of items, because a cap with no overflow rule would mechanically force the conductor to hide a decision. Reading the 1-3 line cap here as applying to the whole turn, decisions block included, would put this file in direct contradiction with that kernel paragraph. It does not: the cap governs `State`/`Running`/`Blocked` only.

Before DS-171, this prose cap was narrower than what a mechanical hook backstop (§9) additionally bounded. `hooks/enforce-turn-shape.py`'s volume check (DS-151) computed a single whole-message CHARGE - every non-blank line, in either the status region or the `## Operator decisions` region, contributed 0 or 1 to the charge unless it participated in one of three named, individually-capped free pools (aggregate fenced content in the status region, well-formed `Waiting:` lines when stoppage is the sole warrant, and up to `ITEM_FREE_LINES` lines per recognized decision item) - and compared that single number against one flat budget, `BASE_BODY_BUDGET = 10`, regardless of which warrant was present. DS-171 retired that check entirely, along with `_turn_charge`/`_volume_flag` and the constants that fed it - see §9's Volume check bullet. The prose rule itself is unchanged: it states the *target* shape for the common case (a status turn should need at most 3 lines). What is gone is the mechanical backstop that used to catch sprawl generally when the target shape was not followed; that backstop's function is now carried by the `dinostack` Claude Code output style (§5), with no hook-level equivalent for non-Claude-Code harnesses. See §9 for the retired charge model's historical definition.

### Answer turns

An Answer turn (Answer warrant PRESENT - see §2 warrant 4) is prose, and the prose IS the payload: no identity line, no status slots, no line cap. This is deliberate, not a gap in the structured shape: "structured outputs are most useful during the actual implementation phase, but during planning not as much," and an operator's direct question deserves a real answer, not a slot template built for status reporting.

If `## Operator decisions` is also present on the same turn (an Answer that also surfaces a decision), it still goes last and still ends the turn - the Answer exemption covers everything ABOVE that heading, never its placement. The heading's own placement-last rule (§4 execution-turn item 3, `content/sections/02-delegation.md`) is universal across both turn shapes.

Answer-turn prose is not exempt from all discipline, only from the structured-shape requirement - see §5 for the relevance rule that governs what the prose may say.

## Length discipline

**Scope: this section governs the conductor's IN-SESSION TURNS. Durable artifacts - PR bodies, tracker comments, source comments, commit messages - are governed instead by `content/rules/conventions.md` §Writing Style and its `### Length discipline` subsection, not by anything here.** The two sections share a name and do not share a scope; both are cited by section name deliberately, never by line number, since either may move. **One carve-out runs the other way, and it is stated on both sides so neither reads as claiming exclusive jurisdiction:** that subsection's emphasis-budget rule ("Emphasis is a scarce budget, not a per-item defence") explicitly names a turn to the operator among the artifacts it covers, so it reaches in-session turns too. Nothing else there does.

This section supersedes and absorbs `.agentic/memory/keep-conductor-updates-short.md` into the always-loaded reference tier. Length is not the discipline it imposes: a LONG answer to a hard question PASSES, a THREE-LINE answer padded with an opening phrase FAILS. Length was never the actual defect, filler was.

**One rule governs what a turn may contain.** Operator attention is the scarce resource this file exists to guard, and every turn the operator reads spends it. A turn is written only when a warrant fires (the four warrants above); that same test then applies to every item INSIDE a warranted turn, which is why a legitimately-warranted turn can still carry an illegitimate item. The test is **form-independent**: content carrying no warrant does not become admissible by changing its form - not by moving position, not by dropping a label, not by rephrasing. If the operator cannot act on it, it does not go in the turn, however true it is. Work already done and already fixed is not a warrant. The diagnostic: if the operator would have to ask "how does this apply to me", the item failed the test. Excluded content is routed, not discarded - to the PR body, the plan artifact, or a memory file.

The rule is stated as a test rather than as a list of banned shapes because a list gets evaded one shape over: every shape below was added here only after a real conductor turn evaded the shapes already named. They are illustrations of the one rule, not additional rules with their own scope, and the rule reaches shapes not named here.

- **Answer relevance.** On an Answer turn every sentence must be load-bearing for the question asked. Restating the operator's question before answering, an opening preamble ("Good question", "Let me look at that", "Here's what I found"), narrating what the conductor is about to do instead of doing it, alternatives or trade-offs or caveats nobody asked for, a closing recap of what was just said, and self-assessment of the answer's own quality or confidence each carry no warrant. Confidence is the sole exception, and only when it IS the question - at which point it is the answer, not an assessment of one. The routing clause applies here too: reasoning, trade-offs, and rejected alternatives belong in the PR body, the plan artifact, or a memory file, not the chat turn.

   **Answer-first ordering.** An operator reads an answer turn for exactly one of three purposes: to make a decision, to unblock an agent, or to understand a result. The first sentence of the turn is that purpose's payload and nothing precedes it - the recommended action for a decision, the instruction or the missing fact for an unblock, the result itself for an understanding. Everything after it exists only to support it: evidence, then scope, then limits. A sentence that would remain equally true and useful with the first sentence deleted is not support and does not belong in the turn. **This is an ordering and excision rule, not a volume rule:** a long answer to a hard question is correct and this rule never licenses shortening one - length itself is not the discipline on an Answer turn.
- **Self-narrating candor.** The framing carries no warrant even when the fact it wraps does. Do not announce that you are about to disclose something, frame a disclosure as honesty, or contrast the honest thing you are doing with a dishonest alternative you did not take - "two things I want to be straight about rather than let you find later", "I'd rather have that stated honestly than have a stubbed test that passes no matter what", "two things I will not assert". State the fact once, plainly, and stop.
- **Editorial addenda.** An editorial addendum is any item the conductor selects into a turn that carries none of the four warrants, whether or not it is bundled or labelled. A labelled package of conductor-selected observations - "Two things worth your attention", "One thing worth noting", "Worth flagging", "Three things stand out", "A couple of observations", or any other invented label for the same shape - is the canonical form of the violation, not its boundary: a single unlabelled warrantless paragraph is the same item. **Position is not part of the shape** (corrected: this was previously scoped to a "trailing" section, and a real conductor turn evaded it by OPENING a section with "Two things worth your attention." instead of closing with one). An item that is merely interesting, or that describes how the work went, carries no warrant however true it is. A fact that genuinely matters - a bypassed gate, an accepted risk, a decision taken, a limit - belongs in the sentence where it is relevant, not in a labelled package; if it cannot fit into the substance of the answer, it is usually not worth the turn.

   **Disposition.** A process observation about how the work or a review loop went - a defect that relocated instead of recurring, a round that cost more than it returned, a placement that consumed headroom - is real content with a real destination: the PR body, alongside its `## Review rigor` section (appended by `/ds-implement-ticket` Phase 11d - see `content/commands/ds-implement-ticket.md`, which records Brief/Plan path, Skeptic round count and tier, and the findings tally), where a reviewer reads it in context rather than an operator reading it mid-session. This is the same routing the Answer-relevance instance above applies to rationale and trade-offs ("the PR body, the plan artifact, or a memory file, not the chat turn"), and that the governing rule states for all excluded content. An observation that changes what the operator would do is NOT thereby a `## Operator decisions` item: treating it as sufficient is how a derivable-default item gets routed into the decisions block instead of being resolved. Admission is governed solely by the Operator-decisions rule in `content/sections/02-delegation.md` ("Operator decisions go last in the turn"). Read the gate at that site and apply it there; it is the single normative statement of the admission conditions, and this file deliberately does not restate them, in full or in summary. A paraphrase here would be a second place for the gate to drift, which is the same argument the "not restated here, unchanged" disposition below makes for the `(Recommended)` marker convention.
- **Announced follow-on work.** Naming work the conductor intends, could, or recommends doing later - "Follow-on work:", "Next I'll...", "Up next", "Remaining work:", "I'd suggest we also...", under any label. If the work is identified and in scope, do it in the same turn under normal risk classification; announcing it is itself the violation, not merely deferring the work, even when the conductor genuinely intends to do it next. Two carve-outs, both of which mark where a warrant genuinely DOES fire rather than carving an exception out of the test - stated because the shape above is otherwise easy to over-apply to them: a genuine blocker the conductor cannot resolve is still the Stoppage warrant or a one-line `## Operator decisions` item (a single stated blocker is legitimate, a menu of optional next steps is not), and the final-completion scope statement ("what shipped, where it landed, what is left") is legitimate - stating what is left OUT of scope on a completion turn is not the same as listing work the conductor could do next.

**Mechanization status (DS-ANSWERFIRST, superseding DS-171).** **The always-loaded carrier is the kernel paragraph in `content/sections/02-delegation.md`, not the `dinostack` output style.** DS-171 moved the status-only, volume, and answer relevance rules onto that output style (`content/output-styles/dinostack.md`), together with self-narrating candor and editorial addenda - the latter covering any conductor-selected item that carries none of the four warrants, in any position in the turn and whether or not it is bundled. That assumed the style was always injected. It is not: `.claude/install.sh` installs it but never writes `outputStyle` to `~/.claude/settings.json`, and an UNSELECTED output style is injected nowhere, so those rules reached no harness at all between DS-171 and DS-ANSWERFIRST. The kernel paragraph replaces it as the carrier and reaches all six harnesses rather than one, so **non-Claude-Code harnesses (Codex, Gemini, Cursor, Kimi, OpenCode) now DO see the proactive statement** - the reverse of what this paragraph previously recorded. The output style is kept and updated in step, not deleted, and remains a genuine second carrier for any operator who does select it: `docs/overview/vision.md` Pillar 8's deletion clause requires a MEASURED zero yield, and "never selected on one machine" is not that measurement. This file remains the normative statement of every rule above, on every harness. **Hook status:** `_status_only_flag` is RESTORED and BLOCKING (see §9's Hook contract - it is a structural predicate, not a phrase matcher); `_answer_relevance_flag` and `_turn_charge`/`_volume_flag` stay deleted. **Of the instances above, answer relevance (including its answer-first ordering clause), self-narrating candor, editorial addenda, and announced follow-on work are mechanized by no regex and no hook, deliberately.** A real answer necessarily reuses key nouns from the question it answers, so no heuristic separates legitimate lexical overlap from genuine restatement, or a caveat the operator actually needs from one nobody asked for; narrating-instead-of-doing, self-assessment, and answer-first ordering are judgments about what a sentence is *doing* and what it is FOR, not matchable phrase shapes; and the addendum and follow-on shapes are exactly the ones an invented label always evades a curated phrase list on. Every candidate mechanization for these four reduces to an enumeration of banned shapes that grows one entry per incident - the Pillar 8 smell - or to a semantic judgment Pillar 7 forbids left-shifting. Enforcement for them is review. See §9 for the full hook contract and `content/output-styles/dinostack.md` for the secondary carrier.

Of the six bullets this section absorbed from `.agentic/memory/keep-conductor-updates-short.md`, three are now carried by the warrant test and the shape rules above ("1-3 lines, result first, no preamble or recap"; "progress pings: one line or say nothing"; "do not explain reasoning or rejected alternatives unless asked"). The three that are not survive here on their own terms:

- *"Surface a finding only when it changes what the operator would do. 'Worth knowing about' is usually not."* - **stays verbatim, unchanged.** This is an emission-gate rule (does the finding warrant a turn at all, §2), not a shape rule, and neither turn shape supersedes it.
- *"`## Operator decisions`: the recommended action and one line of why. Nothing else."* - **not restated here, unchanged.** `content/sections/02-delegation.md` and `content/references/delegation-detail.md` §Operator Decisions Block Rationale both already cover this in fuller form (the recommendation-plus-confirmation shape, the "(Recommended)" label convention, the ban on co-equal ballots). A third copy here would be a third place to drift, and this holds regardless of which turn shape the decisions block terminates.
- *"Final completion: what shipped, where it landed, what is left. Not how it was built."* - **stays verbatim, unchanged.** A Completion-warrant execution turn states this in its status slots (no room for "how it was built" prose to leak in); if a Completion warrant co-occurs with an Answer warrant, the same discipline governs the Answer-turn prose instead.

Closing line, verbatim, and now read as governing relevance rather than a raw count: *"Length is the default failure mode here, not brevity. When unsure, cut."* On an Answer turn this means cut what is not load-bearing, not cut until short.

## Worked example - a normal turn

```
DS-123 · fix/foo · [phase: skeptic-review]
State: 2 of 3 units merged, unit 3 in review
Running: skeptic on unit 3 (~4 min)
Blocked: nothing

## Operator decisions
1. <action> (Recommended) - <one line why>. Reply STOP to skip.
```

The `(Recommended)` marker is mandatory on EVERY item under the heading, single-item lists included. The item count is irrelevant to the rule: an unmarked item is already a violation whether it stands alone or sits beside a marked one. As with the admission conditions above, `content/sections/02-delegation.md`'s Operator-decisions rule is the sole normative statement of the marker requirement - read it there, and do not infer the rule's content from what any hook happens to catch. Whether the abdication guard's ballot check (`_is_prose_ballot`) fires on a given turn is a detection limit, never a licence: a turn the hook lets through is unenforced by the hook, not permitted by the rule, and the hook's silence is not something a conductor may act on. The runtime consequence is the lesser reason to comply in any case - the shape shown here is exactly what a second item, added later without noticing the marker was missing, turns into a co-equal ballot. Mark the recommended action every time, regardless of item count.

## Worked example - an Answer turn

The operator asks a direct question mid-session. This is the Answer warrant, and the entire turn is the answer - no identity line, no status slots:

```
The Phase 7 quality-gate loop caps at 3 fix-attempt rounds before it surfaces a
BLOCKED to the operator; a 4th failed attempt does not trigger a silent 4th
retry.
```

No identity line, no `State:`/`Running:`/`Blocked:` slots, no line cap - the answer is exactly as long as the question requires and no longer. If the operator's question also produced a genuine decision to surface, `## Operator decisions` would still be appended last, per §4's Answer-turn rule.

## Worked non-example - narrative prose beyond the structured slots

**REJECTED under the new rule (this is the shape DS-156 exists to remove):**

```
DS-140 · fix/bar · [phase: skeptic-review]
State: unit 2 merged, unit 3 skeptic sign-off received

Nice, that closes out the last blocking finding from round 2. I went ahead and
kicked off the PR now that everything is green, and I'll keep an eye on CI -
should only take a few minutes given how small this diff is. Let me know if
you want anything else looked at while that runs.

## Operator decisions
1. Merge PR #612 once CI is green (Recommended) - all checks passing, sign-off
   received. Reply STOP to hold.
```

This is a Completion-warrant (unit merged) turn carrying a narrative paragraph between the status slots and the decisions block - exactly the shape the operator's original complaint named: "all it did was add structured outputs to the top and then just still all the normal prose responses is still there." Under §4, an execution turn's status region may contain only `State:`/`Running:`/`Blocked:`/`Waiting:` lines; the paragraph above is neither, so this turn is a shape violation regardless of which execution warrant fired. `_execution_prose_flag` (§9) is the mechanical check that catches this shape, blocking.

**CORRECT behavior for the same moment:**

```
DS-140 · fix/bar · [phase: skeptic-review]
State: unit 2 merged, unit 3 skeptic sign-off received

## Operator decisions
1. Merge PR #612 once CI is green (Recommended) - all checks passing, sign-off
   received. Reply STOP to hold.
```

Nothing in the middle paragraph was load-bearing for the operator's next action; it was commentary. Drop it.

## Worked example - forced yield

When all work is with background agents and the conductor must end its turn - no decision, no completion, no answer pending, only a stoppage on background work - the turn collapses to a `Waiting:` list:

```
DS-123 · fix/foo · [phase: skeptic-review]
Waiting: skeptic - unit 3 correctness review
Waiting: qa-engineer - unit 3 browser scenarios
```

One `Waiting:` line per agent, naming the agent and what it is waiting for. Nothing else. No state recap, no phase narration, no next-steps, no "meanwhile" commentary, no restating what was already reported in a prior turn. The operator's requirement, as recorded in ticket DS-122: *"It should list the agents it's waiting on and why and that's it. Not a whole bunch of extra stuff, only the important and necessary information always."*

Each `Waiting:` line should stay <=120 characters (`WAITING_LINE_MAX_CHARS`) to count as well-formed by the length-discipline rule above. Before DS-171 this bound also governed free-of-charge status in the now-retired turn-charge volume check (§9's Volume check bullet), scoped further than the character bound alone: a well-formed `Waiting:` line was free ONLY when `stoppage` was the SOLE warrant present on the turn (DS-151 amendment A1) - the moment any other warrant (decision, completion, answer) co-occurred on the same turn, `Waiting:` lines reverted to charging like ordinary lines instead of staying free. That accounting mechanism no longer exists; `WAITING_LINE_MAX_CHARS` today is a length-discipline target only, carried by the `dinostack` output style for Claude Code and by this file's prose for every harness, not a hook-enforced charge.

## Worked non-example - the silent continue

**REJECTED (INVALID - no warrant):**

```
DS-123 · fix/foo · [phase: engineer-spawned]
State: engineer returned unit 2, spawning skeptic now
```

This carries no decision, no `Waiting:` line, no completion phrase, and answers no operator question. It is a status ping, and per Rule B it should not have been written at all.

**CORRECT behavior for the same moment:** say nothing. Spawn the skeptic and keep working. The next turn written is whichever of the four warrants fires next - most likely the skeptic's findings surfacing a decision, or a forced-yield `Waiting:` turn if the conductor's own work is now exhausted and only background agents remain.

## Edge case: interaction with the abdication guard

This section documents an **interaction**, not a "no conflict" - the honest claim is that the two hooks never contradict, not that they are unrelated. `hooks/enforce-no-abdication.py` runs three classifiers OR-gated together: `_is_abdication` (the classic permission-seeking interrogative), `_is_stalled_surface_and_proceed` (an announced-then-unexecuted default), and `_is_prose_ballot` (a co-equal ballot lacking a `(Recommended)`/`Recommendation:` marker). The turn-shape hook described in §10 below is a separate mechanism. Three points establish how they relate:

1. **Severity is no longer uniform across the turn-shape hook itself (DS-156).** `_execution_prose_flag` (the execution-turn structural shape check, §9) is BLOCKING: it can exit non-zero and block the current stop, the same category of outcome the abdication guard produces. This is the hook's ONLY remaining BLOCKING check as of DS-171 - but that is no longer true either: `_answer_relevance_flag` (the former Answer-turn ban 2/5 check) stays retired, while `_status_only_flag` (the zero-warrant check) was RESTORED as a second BLOCKING check by DS-ANSWERFIRST (§9's Hook contract). So this is no longer "only one of two checks inside the turn-shape hook can ever block a turn" - it is "the one remaining check can, and the abdication guard always could." See §9 for why the split originally landed there and why the advisory half was later retired outright.
2. **The axes are disjoint.** The turn-shape hook inspects structural shape and *warrant presence* - whether a `## Operator decisions` heading exists at all, a boolean. It never inspects whether individual decision items carry a `(Recommended)`/`Recommendation:` marker; that inspection belongs exclusively to `_is_prose_ballot`. Because the two hooks check different properties of the text, they cannot contradict each other - at most both fire additively on the same turn (an "operator-decisions item sprawl" finding from one, a "fix your ballot markers" finding from the other, both legitimately triggerable by the same sprawling, unmarked decisions block), and those two findings are never mutually exclusive.
3. **Convergent steady state.** A spec-compliant turn - correct fixed-slot shape, and any `## Operator decisions` items carrying a `(Recommended)` marker - suppresses `_is_abdication` (a documented negative-gate coupling: the marker is one of the tokens `_is_abdication` inspects) and suppresses `_is_prose_ballot` (no unmarked items to flag). The turn-shape hook's own forced-yield shape check is separately gated off in this case because the `decision` warrant is present. All three mechanisms independently agree there is nothing to flag on a correctly-shaped turn - arrived at by two unrelated code paths, not by one hook deferring to the other.

State plainly: **a silent continue is the opposite of abdication.** The abdication guard fires on permission-seeking language and on an announced-then-unexecuted default. It never fires on silently continuing work with no turn written at all - that is exactly the behavior Rule B (§2) mandates for the non-warranted case, and the two mechanisms agree on it.

## Hook contract

`hooks/enforce-turn-shape.py` mechanically implements the warrant/shape checks in §2 and §4, plus the operator-decisions per-item sprawl check (§7). As of DS-171 it no longer implements the relevance (§5) or volume rules - those moved to the `dinostack` Claude Code output style, see the note at the top of §5 above and the history note at the end of this section. It does NOT implement the execution-turn identity-line convention (§4) - that was removed, not merely left unimplemented; see the history note at the end of this section. This subsection describes the CONTRACT the hook satisfies as of DS-171.

**Two checks, two enforcement postures (DS-156, operator decision - overrides the architect's blanket-advisory recommendation; DS-171 retired the OTHER two checks this hook used to also run - status-only and relevance - leaving these two as the hook's entire remaining surface).**

- **`_execution_prose_flag` - BLOCKING BY DEFAULT (DS-158 narrows this on one sub-finding - see below).** Implements §4's execution-turn structural rule. **This REPLACES `_forced_yield_flag`; it does not run alongside it.** Its domain is NOT a single flat set - it depends on whether `stoppage` is the SOLE warrant present on the turn. **On BOTH branches, the identity line at position 1 is checked for length only (never shape) against the single `STATUS_LINE_MAX_CHARS` definition in §4.** Prior to the markup-blindspot fix (real-corpus turn_0090/turn_0096), this length finding was ALWAYS blocking, with no downgrade path at all. **It now downgrades to ADVISORY when the identity line, treated as one block, itself clears the SAME evidentiary standard the two branches below already use for a status-region block - `_is_answer_shaped_prose`'s average-words-per-unit discriminator AND the `_ANSWER_PROSE_MIN_SENTENCES` (2) unit floor** - a long identity line is not automatically narrative creep; it can be genuine multi-sentence answer content that simply landed on the first line with no line break. A genuine run-on single "sentence" with no recognizable sentence structure (e.g. a stress-test line of one repeated non-word-boundary character) still fails the unit floor and stays BLOCKING - the bound is a property of position 1 itself, not of which branch is running, so this is stated once here rather than restated per branch below:
  - **Sole-stoppage branch.** Inspects every non-blank RAW line after the identity line, fenced or not (`_body_after_identity_line`'s domain - the same one `_forced_yield_flag` inspects today). A line matching the `Waiting:` shape (§4), a well-formed `State:`/`Running:`/`Blocked:` slot line within `STATUS_LINE_MAX_CHARS` (DS-158), or a recognized markdown heading/table row (see the general branch's markup-blindspot bullet below - the same recognition applies here), is permitted there. Prior to the markup-blindspot fix (real-corpus turn_0093), any OTHER line, fenced or unfenced, blocked unconditionally with no downgrade path - unlike the general branch, which already had the DS-158/DS-159 downgrade mechanism. **This branch now uses the same contiguous-block + answer-shaped-prose + whole-turn-aggregate-unit-floor mechanism the general branch uses**, preserving the same anti-laundering property: a narrative-creep block still fails the average-words check right there, per block, and contributes zero units regardless of the aggregate. The identity line sits before this raw-line domain and is covered by the shared position-1 length check above, not by this bullet.
  - **General branch (decision and/or completion present, with or without stoppage).** Inspects only the unfenced lines of the fence-aware status region (`_segment`/`_regions`). `State:`/`Running:`/`Blocked:` slot lines, `Waiting:`-shaped lines, and (markup-blindspot fix, real-corpus turn_0267/turn_0314) a markdown ATX heading (`#` through `######`) or a pipe-delimited table row (a data row or its `---` separator row) are permitted in the status region; anything else unfenced is flagged, and a permitted slot line exceeding `STATUS_LINE_MAX_CHARS` is flagged the same way regardless of otherwise matching the whitelist shape (this length finding BLOCKS unconditionally) - the identity line's own length is covered by the shared position-1 check above, not restated here. `Waiting:` lines are exempt from this length bound by design (see §4). A recognized heading or table row that is AT OR UNDER `STATUS_LINE_MAX_CHARS` is skipped entirely, same as a slot/`Waiting:` line - it breaks block contiguity and is never folded into a block's word/unit count, closing the false positive where a short, entirely legitimate heading ("## /ds-wrap complete") or a compact status table formed its own low-word-count block and failed the average-words discriminator purely because it is not a sentence, not because it is narrative creep. **A heading/table row OVER `STATUS_LINE_MAX_CHARS` is NOT treated as exempt structure at all - it is a length violation and BLOCKS immediately, exactly the same way an over-length slot line already does (Skeptic Major 1: a single arbitrarily long narrative line prefixed `## ` or wrapped in `| ... |` previously produced NO block and NO advisory finding at all, since it was one recognized, skipped line the line-count volume check never separately measures the length of - the same margin gap DS-156's `STATUS_LINE_MAX_CHARS` bound on the identity line was built to close).** This recognition is bounded on a SECOND, distinct axis too, and the two must not be conflated (Skeptic Major 2): a heading/table row was skipped by this STRUCTURAL shape check but was NOT exempted from the separate CHARGE model (`_volume_flag`) described below, which was a LINE-COUNT budget, not a per-line length bound - an unbounded SPRAWL of many separate, individually well-formed-length heading- or table-formatted lines still tripped the then-existing ADVISORY turn-volume check at `BASE_BODY_BUDGET`. DS-171 retired that volume check outright (see the Volume check bullet below), so this second axis no longer has any hook-level bound at all today - only the length axis described in the previous sentence, closed directly in the structural check itself, remains live. Recognition is also not a fixed label vocabulary the way `State:`/`Running:`/`Blocked:` is; a well-formed-length heading/table row's CONTENT remains as unbounded as a well-formed-length slot line's content already is - both are bounded on SHAPE and LENGTH, never MEANING (see the Known uncovered shapes table below for the parallel slot-line disclosure). Fenced content in the status region is outside the check's domain - see the Known uncovered shapes table below. **DS-158: an unrecognized line's finding BLOCKS by default, but downgrades to ADVISORY when EVERY CONTIGUOUS BLOCK of unrecognized content is itself answer-shaped prose** per `_is_answer_shaped_prose` (§4) - genuine multi-unit explanatory prose, not narrative-creep noise, classified PER contiguous block (a recognized slot/`Waiting:`/heading/table-row line or a fence boundary breaks contiguity) rather than as one flattened union of the whole status region. The narrative-creep case that motivated blocking in the first place still blocks (see `hooks/tests/test-enforce-turn-shape.py`'s `s5c-b`/`ds158-d`), and a non-contiguous mix of narrative creep and a genuine answer paragraph in the same turn still blocks too (see `ds158-f`). **DS-159: "answer-shaped prose" per block now means the average-words-per-unit condition ONLY - the minimum-unit-count condition moved to a WHOLE-TURN AGGREGATE (sum of units across every block that clears the average, compared against `_ANSWER_PROSE_MIN_SENTENCES`), evaluated once in `_execution_prose_flag` itself rather than inside `_is_answer_shaped_prose` per block** - see §4 for why the per-block average stays load-bearing while the count floor does not, and `ds159-a`/`ds159-b` in `hooks/tests/test-enforce-turn-shape.py` for the fixed shape (a real multi-paragraph answer, or a single weak paragraph sandwiched between two strong ones, both now downgrade).
  On a BLOCKING finding, the process ALWAYS exits 0 - it is the `{"decision": "block", ...}` JSON payload printed to stdout, not the process exit code, that blocks the current stop and injects a directive to reshape the turn, the same convention `enforce-no-abdication.py` uses. On a DS-158 downgraded finding, the process instead emits the SAME `additionalContext` shape `_answer_relevance_flag` used, before its own DS-171 retirement (below), and never blocks. **A non-zero exit here would be swallowed silently**: the registration string is `test -f <script> && python3 <script> || exit 0` (`.claude/install.sh`), so a hypothetical non-zero exit on a finding would trip the `|| exit 0` fallback and the block would never reach the harness - do not "simplify" this to a non-zero exit in a future revision. This is the same class of outcome the abdication guard already produces, not a new mechanism. It additionally catches the structural violation the worked non-example above shows (a Completion-warrant turn with narrative prose in its unfenced status region), which `_forced_yield_flag` never inspected because that check only ever ran on sole-stoppage turns.
- **`_answer_relevance_flag` - RETIRED (DS-171).** Previously implemented the answer-relevance instances (opening preamble, closing recap) against Answer-turn prose via curated phrase-list regexes, ADVISORY-only. Deleted, along with the `_OPENING_FILLER_RE`/`_CLOSING_RECAP_RE` phrase lists it consumed - see the mechanization-status note above and the module docstring's Purpose section for why (985/1017 fires over 2026-08-03..08-14 were advisory, never blocking, never changing conductor behavior; a reactive post-hoc nudge could not do what the always-injected `dinostack` output style can). The rules themselves are unchanged; only this hook-level implementation is gone.

**Why `_execution_prose_flag` alone earns blocking (historical - explains why the split existed before DS-171 retired the advisory half entirely).** `_execution_prose_flag` is a structural predicate with no phrase matching or inference involved - a false positive requires the conductor to have actually violated the shape. Advisory enforcement of exactly this structural problem has now shipped three times (DS-122, DS-151, DS-155) and the prose never went away; that is a measured 3-for-3 failure rate for advisory enforcement here, and `docs/overview/vision.md` pillar 2 (verifiable outcomes) treats a hook that logs and exits 0 as having produced no verifiable outcome. `_answer_relevance_flag` stayed advisory (before its DS-171 retirement) because its two mechanized bans were curated phrase lists, not semantic detectors - they mis-fired on novel phrasing, and blocking a genuine answer over an opening phrase like "Good question" was a real friction cost against the same vision pillar's concern for bounded, load-bearing operator interruption. The asymmetry was deliberate, not an oversight: a structural yes/no check earns blocking; a heuristic phrase match does not. **DS-158 does not weaken this argument** - two confirmed false-positive reports showed `_execution_prose_flag` blocking on turns that had NOT actually violated the shape (a `Waiting:` line beside well-formed status slots on the sole-stoppage branch; an unrecognized general-branch line whose content was, empirically, a real answer paragraph, not narrative creep). The fix narrows the STRUCTURAL DEFINITION of a violation on those two specific shapes rather than reintroducing a blanket advisory posture - the narrative-creep case that originally justified blocking (DS-122/DS-151/DS-155) is unchanged and still blocks.

**Non-mechanization of the warrant rule and its instances, with reasoning.** The governing warrant rule and every instance under it are prose-only, deliberately not implemented as regex checks, and none is mechanized now. The reasoning is stated once at the rule itself and is not repeated here; the short form is that each instance turns on what a sentence is DOING or on what was actually asked, neither of which a phrase-list regex has access to, and that the addendum and follow-on shapes are ones an invented label always defeats a curated list on. The `dinostack` output style states the rule proactively under Claude Code, which is the same prose rule surfaced before the turn is written rather than flagged after - a nudge, not a mechanization. This file's prose remains the sole carrier on every other harness. These remain human and model judgment calls, enforced by review.

- **Config toggle.** `turn_shape_guard_enabled` in `.agentic/config.json`, **default ON when the key is absent**, governing BOTH checks together (there is no separate toggle per check). This default is deliberately inverted from `abdication_guard_enabled` (which defaults OFF when absent and requires explicit opt-in): now that `_execution_prose_flag` can block, the risk profile is closer to symmetric with the abdication guard than it was pre-DS-156, but the operator decision retains the existing default-on posture rather than introducing a second opt-in gate for the same hook.
- **Kill switch.** `AE_TURN_SHAPE_GUARD_DISABLE=1` disables per-session, matching the convention used by the abdication guard's own kill switch (`hooks/enforce-no-abdication.py`). Disables both checks; there is no per-check kill switch.
- **Loop guard.** `_execution_prose_flag` uses the existing loop-guard machinery via `hooks/lib/loop_guard.py` (the same two-layer design used by `enforce-no-abdication.py`: the `stop_hook_active` payload flag, and a per-`cwd` counter cap as a backstop for CC bug #54360), bounded by `CONSECUTIVE_BLOCK_CAP = 2` - it must not allow an unbounded block loop on a conductor that keeps writing the same non-conforming shape. Before DS-171 this same machinery also bounded `_answer_relevance_flag`'s advisory re-invocation, sharing one counter/cap with `_execution_prose_flag`; that check is now retired (§9's Hook contract), so the loop guard today governs `_execution_prose_flag` alone.
  - **Bounding re-invocation count does not bound visible duplicate output (DS-155); this residual was historically true for `_answer_relevance_flag`, which no longer exists.** The Claude Code harness does not retract or replace an already-streamed flagged turn when `additionalContext` re-invokes the model - before its DS-171 retirement, the operator saw BOTH the original flagged message AND the corrected re-invocation, back to back, for every single advisory fire. **DS-155 answer-bonus narrowing (not fully closed - a named residual gap remains, disclosed below):** a genuine plain-prose answer to a direct operator question no longer requires the narrow quoted-fragment `answer` shape (`_transcript_answer_bonus`), gated on the most recent GENUINE transcript message looking like a question AND remaining the immediately preceding turn boundary - no genuinely separate, earlier completed assistant turn since it was asked (`_has_intervening_assistant_turn`). This recency check has been rewritten three times against demonstrated false positives, each measured against a local Claude Code transcript corpus (900 files / ~1,623 completed-turn evaluation points, unless noted otherwise) rather than assumed from a hand-built fixture:

- Round 3 tried to exempt the model's own earlier "narrate, then call a tool" step from counting as a competing intervening turn, keyed on an assistant entry whose content array mixed a `text` block and a `tool_use` block in the SAME entry. **DS-156: the completion warrant was widened against a measured corpus, the same discipline as the DS-155 answer-bonus work above.** The reported symptom: a turn opening with a bolded `Done.` and reporting a genuine finished multi-step operation was flagged status-only, because the pre-DS-156 `completion` warrant matched only `[phase: complete]` or a small hardcoded phrase list. - Round 1 tried 7 candidate phrases matched ANYWHERE in the turn, including a `merged/shipped and (live|deployed)` phrase, measured against the UNFILTERED corpus (1,231 turns already flagged status-only). - Round 2 (shipped as commit `cf6bc9d5`) moved the past-participle phrase, plus a new leading "X is done/complete" sentence pattern, to match the identity line ONLY (a string-start anchor, never scanned line-by-line through the body).
