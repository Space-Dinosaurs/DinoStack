# Obsolescence Signal - Floor vs. Dial

## The test

Model-capability changes move the risk-profile dial, they never remove an enforcement floor. Enforcement floors - hooks and hard behavioral rules with no graceful degradation (the abdication guard, tier enforcement, the singularity guard) - stay universal regardless of model capability; a stronger model makes a floor cheaper to satisfy, never optional. Prose dials - how much detail, emphasis, restatement, or worked examples a rule needs - are written for the weakest model actually assigned to the agent carrying that rule (its `model:` tier on Claude Code, plus the models the non-Claude adapters run for it; for content the main session loads directly - `content/sections`, `content/rules` - this is the weakest main-session model across supported harnesses), not for the weakest model the methodology could conceivably support and not for the current frontier model. A model-driven claim ("the model no longer needs this detail") may justify condensing or removing a dial, but only after measuring the claim against that weakest assigned model; it never justifies removing a floor. Removing pure within-file duplication - the same rule stated twice - needs no such measurement, since the rule itself survives; only narrowing a dial's content does. When evaluating an "obsolescence" claim (a newer model makes gate X unnecessary), ask two questions first: is it harness-driven or model-driven, and is it a floor or a dial? Only harness-driven vestiges are retirement candidates.

This is the mandatory pre-filter for `/ds-prune-harness`: apply it to every candidate before it enters the proposal. A rule or hook that enforces a floor is never a deletion candidate regardless of which signal fired.

## Applying the test

Two questions, asked in order:

1. **Harness-driven or model-driven?** A harness-driven vestige exists because of a limitation in the tooling around the model (a stale API shape, a workaround for a harness bug that has since been fixed, a fallback path for a capability the harness no longer lacks). A model-driven claim rests on "the model is smarter now": that claim never justifies removing a floor, because a floor was never written for any particular model's capability. Against a dial, a model-driven claim may justify condensing or removing it, but only after measuring the claim against the weakest model actually assigned to the agent carrying that rule - not the weakest model the methodology could conceivably support, and not the current frontier model.
2. **Floor or dial?** A floor is a rule whose violation is catastrophic or silently unrecoverable if skipped (an enforcement hook, a hard behavioral rule with no graceful degradation). A dial is a rule whose strictness can vary with capability (how much detail a prompt needs to spell out, how many worked examples a rule needs to land correctly). Only dials move with model capability, and only after the measurement in Question 1. Floors do not move.

A candidate that enforces a floor fails the pre-filter and must not be proposed for deletion, regardless of whether the driver is harness or model. A harness-driven dial (or a pure harness workaround with no floor role at all) is eligible to proceed to the signal checklist. A model-driven dial candidate is eligible to proceed to the signal checklist only once measured against the weakest model actually assigned to the agent carrying it; a model-driven floor candidate is never eligible.

## Worked examples (this repo)

**Harness-driven vestige (retirement-eligible):** a fallback path written to compensate for a harness bug or missing capability that has since shipped - for example, a prose instruction telling agents to manually re-derive a value because the harness payload did not expose it, once the harness starts exposing that value directly. The rule exists only because of a tooling gap; once the gap closes, the workaround has no remaining job. This is the shape Signal 5 ("orphaned fallback text") is built to catch, and it is the class the floor-vs-dial test clears for further review, not the class it protects.

**Model-driven floor (never a candidate):** the abdication guard (`hooks/enforce-no-abdication.py`) and the tier-enforcement / singularity-guard hooks. These exist because even a highly capable model will, under specific conditions, abdicate a decision back to the operator instead of proceeding, or attempt to shortcut required review. A stronger model may trigger these guards less often, but the guard itself does not become unnecessary - a floor has no dial component to narrow, and it is never removed on model-capability grounds. Zero fires in a measurement window is evidence the guard is cheap to satisfy, not evidence it can be removed; per this document's own test, this is exactly the model-driven-floor case the pre-filter is designed to exclude.
