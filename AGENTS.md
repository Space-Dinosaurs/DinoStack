# dinostack

A portable package of the agentic engineering protocol for AI-assisted software development. It provides a structured delegation model, risk classification, adversarial review loops, code quality gates, git workflow conventions, and named agent definitions.

A `diverged` status requires BOTH `behind>0` AND `ahead>0`; ahead-only is not divergence. Full status taxonomy and recovery guidance: `content/references/base-branch-sync.md`.
- Hooks-snapshot dogfooding-gap closure (DS-54 follow-up): a merged hook fix stays dormant on this machine until an installer re-syncs the snapshot - the SessionStart nudge only fires at a brand-new session's first tool call, never mid-session or at merge time. Three mechanisms now close it: `bin/ds-doctor`'s `check_hooks_snapshot_staleness` check (on-demand; `--fix` calls `sync_hooks_snapshot`, the identical call every adapter `install.sh` already makes unconditionally; `half_applied` is NOT reported resolved by that sync alone - it only refreshes snapshot content, never an adapter's own hook config, so `--fix` on `half_applied` reports it unfixable with an actionable "re-run that adapter's install.sh" message; a nonzero exit from the classifier is a WARN, never a silent OK); `bin/ds-base-sync`'s non-blocking advisory note after every invocation (the one guaranteed post-merge trigger point, since Phase 12 calls it unconditionally; read-only, never mutates); and `bin/ds-update`'s `_hooks_snapshot_diverged` check, which forces the adapter-install loop on its `old_head==new_head` early-return path when the live hooks/ source hash diverges from the snapshot's stored hash - closing the case where an operator manually `git pull`ed a hooks change before running `ds-update`, leaving no diff for the normal rebuild-trigger logic to see (`scripts/update.js`, the interactive updater, has no direct equivalent on this path - it relies transitively on its own unconditional `runDoctor()` call instead). None of the three can auto-rewire a live session's hooks from a passive trigger - only an explicit `--fix` or an adapter `install.sh` run ever calls `sync_hooks_snapshot` (the DS-54 invariant). All three hashing call sites (the sync writer, the SessionStart classifier, and `ds-update`'s divergence check) call the SOLE `hooks_source_paths` function in `scripts/lib/hooks-snapshot.sh` - never a hand-copied path list. Friction cost: any operator with uncommitted local `hooks/` edits gets the full adapter-install loop forced on every `ds-update` "already up to date" run (the live hash differs from the last sync by construction) - expected, not a bug. Full detail: `hooks/AGENTS.md` §Downstream consumers "Merged is not live". Adapter asymmetry: `.cursor/install.sh` and `.opencode/install.sh` symlink hook config directly into the checkout instead of snapshotting it, so those two harnesses have no dormancy gap at all - Claude Code (the primary harness), Codex, Gemini, and Kimi are the ones subject to it.

- Resident-set budget ratchet (DS-68 redo, #532; redefined for the trigger-loaded methodology, DS-143): `scripts/check-resident-budget.sh` now measures only the post-manifest body of `content/templates/claude-managed-content.md` - the Skill Loading table is the sole content still resident in every session after DS-143 stopped `~/.claude/CLAUDE.md` from `@`-importing `METHODOLOGY.md`/`conventions.md`/`code-standards.md`. Workflow `.github/workflows/resident-budget.yml`, regression suite `bin/tests/test_check_resident_budget.sh`. `check-resident-budget` is a required status check on `main` (ruleset `14778332`, 16 checks total) - the job name is unchanged across the redefinition. THRESHOLD ratchets downward over time - lower it in the same PR as any deliberate shrink of the table; never trust a cited baseline/THRESHOLD pair, run `bash scripts/check-resident-budget.sh` for the live figure. A separate gate, `scripts/check-skill-embed-budget.sh` (regression suite `bin/tests/test_check_skill_embed_budget.sh`), guards the generated `.claude/skills/dinostack/SKILL.md` - the methodology content moved there, not away - three ways: a FLOOR (catches a regression to a pointer-only skill), a CEILING (a safety boundary on the verified-safe injection size, not a tidiness budget), and an embed-completeness check (DS-143 follow-up) that pins `EXPECTED_SECTION_COUNT`/`EXPECTED_RULES_COUNT` against `content/sections/[0-9][0-9]-*.md` and `content/rules/*.md` (excluding `module-manifest.md`) and asserts every one of those files' own top-level heading is present in the built SKILL.md - adding, removing, or renumbering any of those source files fails CI until the matching constant is bumped in the same commit; bump it alongside the file change, same discipline as the THRESHOLD ratchet above. Its CI job `check-skill-embed-budget` is wired into `resident-budget.yml` and IS a required status check on `main` (ruleset `14778332`, one of the 16 contexts counted above alongside `check-resident-budget`) - the count moved from 15 to 16 precisely because this job was promoted.

- Root `MEMORY.md` is intentionally untracked here (DS-129), same rationale as `/decisions.md` and `/.agentic/*` above: it's the methodology's own self-improvement scratch, not a shippable artifact for consumer projects to inherit. `MEMORY-archive.md` is deleted and the archive pattern retired (DS-130, merged) - an archived entry stopped being enforced the moment it left the always-loaded file. Consequently a fresh clone and every worktree-isolated engineer have no `MEMORY.md`; any fact an engineer needs belongs in `AGENTS.md` or the spawn brief, not an assumed local memory file.

- Command file size ratchet: `scripts/check-command-file-budget.sh` measures the raw on-disk byte size of `content/commands/ds-implement-ticket.md` directly (`wc -c`, no build step) - closing the gap left by `check-resident-budget.sh`, which deliberately measures only the assembled resident set and never sees command files at all. That file grew from 233,942 B to 363,761 B in about two weeks with zero shrink commits before this gate existed. Workflow `.github/workflows/command-file-budget.yml`, regression suite `bin/tests/test_check_command_file_budget.sh`. THRESHOLD_BYTES is currently 371,000 B (~2% deliberate headroom over the 363,761 B live figure at gate creation - meant to fire on sustained growth, not the next paragraph). Shares `scripts/lib/budget-gate.sh` with the other two gates, but not identically: all three call `budget_repo_dir`/`budget_file_bytes`, while only `check-resident-budget.sh` and this gate call `budget_report` for the OK/OVER-BUDGET report shape - `check-skill-embed-budget.sh` implements its own two-sided floor/ceiling report inline instead. This gate's own call (`:83`) is the only zero-extra-context `budget_report` caller of the two (`check-resident-budget.sh` passes one extra context line), which is why the bash 3.2 empty-array crash landed solely here. **Advisory, not required**: it is deliberately NOT added to the `main` ruleset's required-checks list - promoting it to a blocking check is a separate operator decision - but the job itself is NOT `continue-on-error`: it fails (goes red, with a `::error::` annotation) on overage like any other check. THRESHOLD_BYTES ratchets downward over time - lower it in the same PR as any deliberate compression of the file; never raise it to accommodate un-triaged growth, and never trust a cited figure - run `bash scripts/check-command-file-budget.sh` for the live number.

## Tools
- GitHub operations: use `gh` CLI - do not use GitHub MCP
- `gh pr create` requires an authenticated `gh` session (`gh auth status`). Run `gh auth login` if needed, then `gh pr create`.
- `rm -rf` is blocked by Claude Code permissions in this repo; remove files individually: `rm <file>` then `rmdir <dir>`
- `bin/ds-memory` - lightweight memory retrieval tool for querying `.agentic/events.jsonl`, `MEMORY.md`, and `.agentic/context.md` on demand.
- `bin/ds-base-sync` - fast-forwards the local base branch after a merge without a checkout; the only mechanism that moves a local branch ref outside an explicit checkout+pull.
- Force-push (`--force`, `-f`, `--force-with-lease`) is blanket-denied by the harness permission layer for subagents AND the conductor; chat authorization does not clear it. Push to a NEW branch name instead of rebasing a branch with an open PR.
- `bin/ds-tracker` - manage the project-local gitignored `.agentic/tracker.yml` overlay (`init` / `set` / `show` / `path` / `resolve`). Applied after the four-step `AGENTS.md` tracker chain: if `AGENTS.md` declares no tracker, or a different one, the overlay is sole source and fully replaces the base (`_source: "overlay"`); it merges field-by-field (`_source: "merged"`) only when both declare the same tracker. Refuses to write to any path git would track; `--force-unignored` overrides.
- The Graphify PyPI package is genuinely named `graphifyy` (double-y); the CLI and skill command stay `graphify`. This looks like a typo and has been "corrected" incorrectly before - it isn't, verified against the upstream README.
- `git checkout <sha> -- <path>` inside a worktree resurrects files a later commit deleted - it updates/adds files present at `<sha>` but does not replay deletions, so files removed downstream of that commit silently reappear (they were never gone from the worktree's disk - it started from `main`). When basing a step on a non-`main` commit this way, explicitly `git rm` anything that commit deleted, and gate on an exact `git ls-files` set rather than trusting the chain.

## Conventions
- **Base branch:** `main` is the sole integration branch for this repo. Declaration: `BASE_BRANCH: main`.
- **Workflow for all implementation work (non-Trivial risk):**
	1. `git fetch origin` to ensure latest `main`.
	2. Spawn subagent Workers using `isolation: "worktree"` with worktrees branched from `origin/main`. Worktree path: `.agentic/worktrees/<branch-name>`.
	3. Worker implements, runs quality gates (lint, typecheck, tests), commits.
	4. Push branch to origin: `git push -u origin <branch-name>`.
	5. Open PR against `main` via `gh pr create`.
	6. Once CI/CD checks pass, auto-merge: `gh pr merge --squash --delete-branch`.
	7. Clean up: isolation worktrees are removed after the branch is pushed to origin; feature worktrees are cleaned up after merge. The session-start prune script and branch-prune block remain as backstops. See `content/references/worktree-lifecycle.md` §Isolation worktree cleanup commands and §Feature worktree cleanup commands.
	8. Update local main: `git checkout main && git pull --ff-only origin main`.
	- Steps 6-8 are automatic - never pause for merge approval when CI is green.
	- `main` enforces strict required status checks: a PR whose base has moved must be rebased and re-run before merge - GitHub does not re-run workflows on base movement. Sync with `gh pr update-branch --rebase`; the default (merge) update produces an unsigned commit that fails the DCO check.
	- Failed CI is a hard stop - investigate before proceeding.
- **Conductor never edits shippable artifacts directly, including Trivial one-line changes.** Every shippable change is delegated to a worktree-isolated `engineer` branched from `origin/main`; the conductor edits only exempt artifacts (`.agentic/`, conductor-direct prints/decisions/resolver execution) in its own checkout. See `content/rules/conventions.md` §Git Workflow for the shippable/exempt classifier.
- Superseding an open PR: close + rebase, never bundle - see `content/rules/conventions.md` §Git Workflow.
- When isolation:worktree Workers are used across multiple sequential spawns in the same task, the worktree is cleaned up between them and subsequent Workers fall back to the main tree. Tell follow-up Workers this explicitly. (tracked separately - see DS-123) - the canonical round-N mechanic that supersedes the close+reopen fallback is now documented in content/rules/conventions.md §Git Workflow and content/references/worktree-lifecycle.md §Round-N rework mechanic.
- When spawning parallel engineer units, each spawn brief must explicitly say "branch your worktree from current `origin/main`, NOT a local checkout that may include not-yet-merged sibling units." Worktree branch leaks (commits landing on the wrong unit's branch) are the most common cross-unit contamination class when parent units have not yet merged.
- Assembling a multi-unit PR: the repo enforces a DCO Signed-off-by check on EVERY commit. Conductor `git merge --no-ff` assembly commits are unsigned and fail DCO - instead cherry-pick each engineer's signed unit commit (no merge commits) or pass `git merge --signoff`. Never force-push to fix unsigned merge commits; `gh pr merge --admin --squash` discards merge commits at merge time anyway.
- When you struggle with a repeatable task (starting dev servers, deploying, running migrations, connecting to databases, etc.) and find the solution, proactively save the working steps to this file (or the relevant subdirectory `AGENTS.md`) so future sessions don't repeat the struggle - root `MEMORY.md` is untracked here (DS-129) and no other session will see it.
- The pre-commit hook does not currently auto-stage `.codex/agents/*.toml`. After any `content/` edit, either stage that regenerated artifact manually or extend the `git add` list in `hooks/pre-commit`. (`.claude/skills/dinostack/METHODOLOGY.md` and, as of DS-143, `SKILL.md` - which now embeds METHODOLOGY.md plus both rules files and so changes on most `content/sections/**` and `content/rules/{code-standards,conventions}.md` edits - are already staged by that hook.)
- A green `bin/tests/` run is not the gate set - the required `hooks-js-tests` check pins methodology prose byte-for-byte and lives outside `bin/tests/`. After any `content/` prose edit, run the hooks JS suite too. It has no single literal command: the job is an inline `for f in hooks/tests/test-*.js` loop that `node`-runs each file, minus whichever files the loop's own `case` arms quarantine into the separate `wrap-lock-tests` job (currently `test-wrap-acquire-lock.js` and `test-wrap-release-lock.js` - re-derive from the case arms in `.github/workflows/hooks-tests.yml`, don't hand-count the glob; a filename containing "wrap-lock" is not by itself evidence of membership - e.g. `test-wrap-lock-abandoned.js`, `test-wrap-lock-session-id.js`, and `test-wrap-lock-verdict.js` all run in `hooks-js-tests`, not `wrap-lock-tests`). Two of those prose-pinning tests are `test-wrap-md-partA-parity.js` (asserts `/ds-wrap` retains its whole-flow lock) and `test-wrap-context-format-golden.js` (sha256-pins `content/references/wrap-context-format.md` from its NORMATIVE marker to EOF).
- **Docs-currency pass is mandatory before any work is declared complete and before its PR merges** - ticket work or ad-hoc, regardless of which paths changed. Enumerate the surfaces the diff touched, then verify and update any related documentation that now states something stale; land doc updates in the SAME PR as the work. Candidate doc surfaces to check: `docs/index.html`, `docs/slides/*.md` (plus rebuilt `.html` via `bash scripts/build-slides.sh`), `README.md`, `CONTRIBUTING.md`, `content/SKILL.md`, and the relevant `AGENTS.md` sections. This generalizes the `content/`-triggered bullet below: that bullet's trigger stays mandatory for `content/` edits specifically, while this pass applies to all work. Record the pass's outcome with the canonical `Doc-sync:` attestation from `content/references/doc-sync-obligation.md` - either `Doc-sync: predicate not triggered (no reality-asserting change).` or the triggered/updated form. Skeptic tiering per `content/references/doc-sync-obligation.md`.
- Any change to `content/rules/`, `content/references/`, `content/agents/`, `content/commands/`, or `content/sections/` MUST also update `docs/index.html` and any affected `docs/slides/*.md` (then run `bash scripts/build-slides.sh` and commit the regenerated `.html` - do not hand-edit the `.html`; upgrading marp is an intentional same-PR action: bump `scripts/package.json` + regenerate `scripts/package-lock.json` + rebuild) in the same PR; additionally, any now-stale count, list, or reference in `README.md`, `CONTRIBUTING.md`, or `content/SKILL.md` is in-scope for the same PR. Public-facing intent debt is the worst kind. The canonical trigger predicate and tiered Skeptic classification for this obligation live in `content/references/doc-sync-obligation.md`; Skeptic flags missing docs sync per those tiers (Major by default, Critical when a public-facing doc actively misleads). Grep the decks by hand: `check-slides-sync` only compares each `.md` against a fresh render, so an assertion that is stale in both the `.md` and its `.html` passes the gate.
- Any new interactive prompt added to `.claude/install.sh` MUST use the `ae_confirm()` helper (reads `/dev/tty` when available, defaults "no"). Never use bare `read -p` - it aborts under `set -euo pipefail` + piped stdin (the `curl | bash` install path).
- After any change to `content/SKILL.md`, run both `.pi/build.sh` and `.claude/build.sh` to regenerate adapter-specific SKILL.md copies. The pre-commit hook does not auto-stage these.
- Mutation-testing a `content/` spec assertion requires `bash scripts/build-all.sh` BEFORE running the test - mutating `content/` alone trips the byte-identity assertion and falsely confirms that a semantic assertion caught the change.
- The `codex-skill-sync` CI gate validates exactly four generated native skills under `.codex/skills/`. After changing a canonical input, review and refresh `.codex/skill-compatibility.yml` with `python3 scripts/codex-skills.py inventory --repo . > .codex/skill-compatibility.yml`, then run `.codex/build.sh`; never hand-edit generated skill files. That redirect truncates `.codex/skill-compatibility.yml` to 0 bytes BEFORE Python runs, so a run that aborts (e.g. `assert_paragraph_rules_reachable()`'s SkillError on an unmatched PARAGRAPH_RULES anchor, or any other inventory-time failure) leaves the committed file empty on disk - `git checkout -- .codex/skill-compatibility.yml` restores the index copy (equivalent to the last-committed copy here since nothing is staged). Prefer redirecting to a temp file and `mv`-ing it into place only on success, or check the command's exit status before trusting the output.
- `REPO_DIR` is distinct from `REPO`: `REPO` is the ticket's own project checkout, `REPO_DIR` is the dinostack / DinoStack install where `bin/`-tools live. Resolve via `scripts/lib/repo-dir.sh` (`resolve_repo_dir`): `repo_dir` from `~/.agentic/agentic-engineering-config.json` when present and a valid git repo, else `~/DinoStack`. Both `bin/ds-resolve-worktree` and `bin/ds-base-sync` depend on it.
- Any local adapter-drift check must copy its pathspec verbatim from the `Fail on adapter drift` step in `.github/workflows/adapter-sync.yml` - the 11 adapter dirs PLUS `.github/copilot-instructions.md`, `.github/agents`, `.github/prompts`, `.github/instructions`, `.github/hooks`. `scripts/build-all.sh`'s `ADAPTERS` array is the build loop, not the diff assertion, and omits those five. `git diff --exit-code` exits 0 silently on a pathspec that does not exist, so a hand-typed list green-lights whatever it misspells or omits.
- Verify DCO author/sign-off with lowercase `git log --format=%ae` (raw). Uppercase `%aE` and `git show` both APPLY `.mailmap`, which displays a mismatched author email on a correctly signed commit.
- Build commits with porcelain `git commit -s`, never `git commit-tree`. The plumbing command takes no `-s`, so the commit silently lacks its trailer and fails the required DCO check, and it skips pre-commit hooks entirely.
- A new module is not done until something in `content/` invokes it. Shipping uncalled and passing every review is the default failure, not the exception - assert the wiring explicitly, as `check_prose_wiring()` in `bin/tests/test_worktree_lifecycle_spec.sh` does.
- `docs/planning/` is gitignored, so a worktree-isolated engineer branched from `origin/main` cannot read a plan there - restate any obligation it carries in the spawn brief, and never keep the same binding prose in both (a fix applied to one copy drifts silently).
- No CI gate checks for em dashes, so scope the check to your own diff, never the whole file: `git diff --cached -U0 | grep '^+.*—'` (staged) or `git diff -U0 origin/main...HEAD | grep '^+.*—'` (branch). A whole-file grep is useless here - 13 em dashes pre-exist on `main` in the resident files (`content/rules/code-standards.md` 5, `content/sections/04-risk-classification.md` 8) and will match on every run. That count is the baseline: leave those alone, and treat any added line that matches as a defect to fix before committing - except the two in this bullet's own grep patterns, which are the literal search target and must not be "fixed" (doing so silently breaks both commands).
- A shell gate whose assertions are guarded by `command -v <tool>` must hard-fail under `${CI}` rather than skipping, or the job goes green having asserted nothing. `bin/tests/test_check_resident_budget.sh:155-156` is the pattern; `.github/workflows/bin-tests.yml:57-58` installs zsh so the guard never fires in CI. A silently-skipped assertion is indistinguishable from a passing one in the job log.
- Editing the `main` ruleset requires the admin `gh` account. Observed once this session: a non-admin token's read of ruleset `14778332` returned `bypass_actors` as empty while the admin read returned one actor. Only the admin half is independently confirmed, so treat any `bypass_actors` array you did not fetch as admin as unverified rather than empty - a PUT built from it can silently wipe the bypass entry. Back up the full ruleset JSON before any PUT and diff field-by-field afterwards.
- Never end a session holding uncommitted `MEMORY.md`/`AGENTS.md` edits - the working tree may be the content's only copy. A worktree-isolated engineer branches from `origin/main` and cannot see these files, so a delegated edit is computed against a stale copy and can silently drop them. Commit in the session that wrote them; confirm sole-copy status with `git log --all -S "<phrase>"` plus `git stash list` (`--all` does not cover `refs/stash`).
- An `isolation:"worktree"` engineer spawn with a named branch can leak that branch into the conductor's own checkout and switch its HEAD - observed corrupting `main` once (a subsequent conductor commit captured the diverted state as mass deletions). After every worktree-isolated spawn, verify the conductor's own checkout is still on its expected branch (`git branch --show-current` + `git status` + `git diff --stat`) before committing anything from it.
- Isolation worktrees always branch from `main` HEAD, never from a named feature branch. A continuation fix meant to land on an existing feature branch can't be briefed as "branch your worktree from `origin/<feature>`" - it will silently start from main instead; cherry-pick or push the commit directly onto the existing branch's remote tip instead.
- After an isolation-worktree engineer commits, the main checkout's view of that branch ref can lag behind the worktree's own HEAD. Pushing by branch name can ship the stale base commit and `gh pr create` will reject it ("no commits between main and branch") - push the explicit commit SHA (`git push origin <sha>:refs/heads/<branch>`), not the branch name.
- An adapter-rebuild/baseline-regen engineer commit, or even a hand-authored feature commit built from a stale local snapshot, can silently revert unrelated source files while green CI does not catch it - a stale isolation worktree once produced a commit that reverted 51 files from three already-merged PRs while every adapter/baseline sync gate stayed green, and separately PR #390/#432 (DS-47) silently reverted unrelated list items, counts, and cross-refs in files it legitimately touched. Verify any "regenerate generated artifacts" commit's diff touches *only* the intended generated paths before merging; diff a PR's base..tip for hunks unrelated to its stated intent before merging or rebasing; after any multi-PR feature lands, spot-check that a key new symbol is actually present on `main`, not just that the PRs show "merged."
- `.claude/install.sh` has a zsh variable conflict: a local variable named `status` is read-only in zsh. Avoid `status` as a variable name in zsh-specific code, and run affected blocks in a bash subshell for mixed-shell compatibility.
- When `origin/main` advances mid-session, a diff against the new `origin/main` can make an unrelated, already-merged PR's files look reverted - this is a diff-base artifact, not a real revert, since your branch predates that merge. Diagnose by comparing your commit's parent to `origin/main`; fix by rebasing onto current main and re-running any generator the newly-merged commits may have changed (adapters, baselines, slides).
- Checking for duplicate in-flight work only at spawn time misses collisions that start (or merge) while a worker is running - two live sessions once independently fixed the same three tickets. Check open PRs and the shared checkout's `git status` before spawning, and re-check for a superseding merge right before opening a PR (a dirty `mergeStateStatus` on a fresh PR is the after-the-fact symptom). When superseded, stand down and cite the superseding PR rather than racing a rebase.
- Four reusable git lessons, all of which have shipped bugs here: (1) to flip a gitignored file to tracked, append a negation (`!.agentic/<file>`) rather than removing the ignore rule - additive negation is safe, removal leaks; (2) a negation cannot re-include a file whose parent **directory** is excluded - `.agentic/`, `/.agentic/`, and bare `.agentic` all defeat `!.agentic/qa.md`; only glob forms (`/.agentic/*`, `**/.agentic/**`) work; (3) matching is **last-match-wins**, so a negation only overrides an umbrella placed **above** it - `bin/agentic-migrate` appended umbrellas at EOF and silently killed every carve-out (fixed #527); (4) `git diff --quiet <ref> -- <path>` exits 0 for a path that has never been committed to `<ref>` ("unchanged", not "new"), so an untracked file is invisible to any gate built on it - pair it with `git cat-file -e <ref>:<path>` (this defeated Part G for brand-new files, fixed pre-merge in #534). Green CI per-PR still doesn't guarantee `main`'s end state under concurrent sessions - assert directly with `git ls-files` / `git check-ignore`.
- Merging to `main` needs exactly 1 code-owner approval, not 3 (verified against the live ruleset: `required_approving_review_count: 1`; CODEOWNERS designates `* @tysonhummel` as sole owner). `--admin` is still required for `gh pr merge` when the PR is authored by @tysonhummel (GitHub disallows self-approval), or no `@tysonhummel` reviewer is present - the normal unattended-agent case. Confirmed merging #483-#486; an approval-required failure on `--admin` means the bypass actor was removed from the ruleset and needs re-adding in GitHub's UI.
- The live Claude Code harness auto-locks every `isolation:"worktree"` worktree at creation. Directory is `.claude/worktrees/agent-<agentId>` (NOT `worktree-agent-<id>` - that's the branch name), branch is `worktree-agent-<agentId>`, and `git worktree list --porcelain` shows `locked claude agent agent-<agentId> (pid <pid> ...)`; a non-force `git worktree remove` already refuses it (`remove -f -f` needed), independent of any methodology-level lock. Any worktree-cleanup detection logic must match the branch-name pattern, not assume the directory path contains the same substring.
- Work in an isolation worktree can silently absolutize the `.claude/skills/dinostack/{agents,commands,references,rules}` symlinks to that worktree's own path - `check-adapter-sync` compares regenerated content and the symlink still resolves fine on the machine that broke it, so an absolutized symlink merged to `main` silently breaks the skill for every other clone. `scripts/check-symlinks-relative.sh` (wired in `adapter-sync.yml` since PR #500) now gates this in CI; before staging, check `git status --short` for those four paths and restore with `git restore --staged --worktree`; audit a landed commit with `git ls-tree -r <sha> .claude/skills/dinostack | awk '$1=="120000"{print $4}'` then `git cat-file -p <sha>:<path>` (a leading `/` means broken). Re-absolutization recurs on every build run inside an isolation worktree, not once - re-check `git status --short` for those four paths before every stage. (DS-96, DS-104)
- A compression/extraction change that moves inline prose into `content/references/*-detail.md` creates a staleness class that merges silently, with no conflict marker: later commits keep patching the original inline location while the extracted copy diverges, and `git merge origin/main` merges it cleanly since nothing else touches that file. That is one hazard - the original site drifting after extraction. The same relocation carries a second, distinct hazard: the extracted block can arrive already wrong, since a verbatim move preserves whatever the block asserted and reviewers read the move as a no-op and never re-check its content; DS-68's relocated prose carried a byte figure that was stale before the move. Catching all instances required a file-by-file audit of every post-branch-point commit, not just ad hoc spotting (PR #420, DS-68). When moving a block into `content/references/`, re-verify every count, path, and figure inside it against live state in the same PR - "verbatim" is a diff property, not a correctness property.
- A verification step that pipes through BSD `xargs -I{}` can assert nothing and still pass: real paths exceed `-I`'s ~255-byte replacement budget, so `xargs` returns rc=1 and emits nothing, leaving the comparator comparing empty to empty. `2>/dev/null` on any comparison step compounds this by converting the tooling failure into a false pass - a green local loop on macOS then proves nothing while CI exercises the real comparison.
- Adapter/methodology build discipline: `content/` is single-sourced into all adapter dirs; any change requires `bash scripts/build-all.sh` (11 dirs) then `git diff --exit-code -- <adapter dirs>`. `content/sections/**` changes also need `scripts/.methodology-baseline.sha256` regenerated. `check-adapter-sync` CI tests the merge result, not your branch - rebase onto current `origin/main` and rebuild before merging.
- Repo checkout convention is `DinoStack`; as of the skill-namespace rename, the SKILL name and every adapter's skill directory are `dinostack` too (`.claude/skills/dinostack/`, etc.) - skill names occupy a flat per-user namespace with no vendor scoping, so an unscoped `dinostack` skill name risked collision with a third-party skill of the same name. Config FILENAMES and the activation marker strings did NOT rename and never will: `~/.claude/agentic-engineering.json`, `~/.agentic/agentic-engineering-config.json`, and the `agentic-engineering: opt-in`/`opt-out`/`-profile:`/`-preset:` marker lines - those markers live in consumer repos we do not control, so renaming them would silently change activation state in projects we never touch. All methodology slash commands use the `/ds-*` prefix (e.g. `/ds-implement-ticket`); `bin/agentic-*` CLI names and their no-slash usage text are likewise unaffected by either rename (DS-26).
- Some `content/` source files are hardlinked (not copied) into their adapter destinations, and this is inconsistent across files - check the mechanism, not a fixed list, which goes stale: grep the target `build.sh` for `hardlink_from_content(`, a bare `ln ` (no `-s`), or `os.link(` - any adapter build whose script calls one of these against a `content/` source genuinely hardlinks it (same inode, mutates in place on a `content/` edit) rather than copying it. A hand-typed snapshot of which scripts/counts this resolves to has repeatedly gone stale here (DS-90 Unit 5 review) - do not restore one. `bash scripts/build-all.sh` is still required after any `content/` edit regardless of hardlink status, since a fresh git worktree checkout breaks all hardlink relationships (git does not track hardlinks - every worktree gets independent inodes) until rebuilt. (DS-78, DS-90)
- Adapter dirs contain hand-authored sources that `build.sh` does NOT regenerate (`.codex`/`.copilot`/`.cursor`/`.gemini`/`.github` hook files, `.opencode/plugins/session-context.ts`) - a "rebuild adapters, skip them" assumption misses these; check them manually after any adapter source edit or cross-adapter pattern change. (DS-26)
- Bulk file sweeps over `evals/` must exclude git worktrees (`evals/.worktrees/wt-*` are pinned at historical commits) to avoid dirtying checkouts; discovered when a sed sweep modified a pinned worktree's tracked files. (DS-26)
- On a GLM session (or any non-Claude model backing the session), spawning a methodology subagent (engineer, skeptic, etc.) fails immediately. Every agent's frontmatter `model:` is a Claude alias that resolves to a `claude-*` model ID the non-Claude key doesn't carry, and the Agent tool's `model` param enum is Claude-only - there is no way to route a subagent to a non-Claude backend. On such a session, don't attempt Worker/Skeptic delegation; go conductor-direct and compensate with mechanical verification, or switch the session to a Claude model first.
- Never include `"mode": "opt-in"` in doc or adapter example JSON unless demonstrating opt-in activation - it silently disables the entire methodology on repos without an `agentic-engineering: opt-in` marker. Show only the field being demonstrated (e.g. `{ "profile": "relaxed" }`) or use `"mode": "opt-out"`.
- Marp dark-theme reskin gotchas (theme leaks, table and code-syntax fixes): see `docs/slides/AGENTS.md`.
- A shell check written as `cmd 2>/dev/null | head -N || echo 'no records'` can never report its negative case: `||` binds to `head`, which exits 0 on empty input, so the fallback is unreachable and an empty result is indistinguishable from a populated one. Same vacuous-pass family as the `command -v` guard and the diff-scoped em-dash check already listed here. Test the branch you expect to fire by making it fire on purpose.
- When a methodology sentence is found to be false, prefer DELETION over a narrowed rewrite, and check first whether anything is load-bearing on it. A narrowed rewrite reads as the careful option but re-asserts the same shape of claim against the same unverified surface: DS-150's replacement for "**Subagents do not have hooks.**" was itself false. Both original sentences were load-bearing for nothing and deletion was the correct fix. Corollary: a claim removed from `content/` is not gone until its `docs/slides/*.md` copy is grepped by hand - `check-slides-sync` compares each deck against a fresh render and passes when the `.md` and `.html` are stale in agreement.
