One conversation, many tickets: DinoStack's conductor and lanes

2026-11-06

Running several tickets at once usually means several terminal windows, each waiting on you. DinoStack's conductor and lanes turn that into one conversation. You talk to a single conductor session. It starts each ticket as its own headless session, watches them, and comes back to you only when one of them needs a decision.

The conductor

The conductor starts from a /ds-ticket-triage plan, which analyses the tickets' dependencies and conflicts and splits them into parallel lanes. From there the conductor:

  • starts each lane and watches all of them,
  • relays your rulings to the lanes they concern,
  • surfaces a blocked or failed lane to you as a decision, and holds risky actions until you rule,
  • re-runs triage over the remaining tickets when a wave is done, and presents the next wave.

It does no ticket work itself. Its state lives in one file, .agentic/runbook-<KEY>.json, which it reads first after a context compaction, so a long run survives one. And no message from the conductor ever tells a lane to skip its own Skeptic review, QA, or gates.

Lanes

ds-lane starts each lane as its own headless Claude Code or Codex session, picking the harness the conductor itself is running in. Up to 5 lanes run at once per repo by default (DS_LANE_MAX); the rest queue and start as slots free up. Each lane ends its work with a LANE-DONE or LANE-BLOCKED marker, so the conductor can tell a finished lane from a stuck one without reading its whole transcript. A lane stopped by a usage limit shows as blocked with the reset time, and resumes later in the exact session it left.

Every lane runs the full ticket workflow

A lane is not a single worker. Each one runs /ds-implement-ticket end to end:

  • an engineer working in an isolated worktree,
  • an adversarial Skeptic review loop with a round cap,
  • a QA agent checking the ticket's qa_criteria,
  • a PR, which can merge on its own once CI passes when auto-merge is turned on.

Running five tickets in parallel therefore means five reviewed, QA-checked PRs, not five unreviewed diffs.

Design choices

  • Lanes don't talk to each other. Every message goes through the conductor, which delivers it with ds-lane send or ds-lane resume.
  • Each lane opens its own PR. There is no separate merge step to coordinate.
  • Stalls are caught mechanically. The conductor runs ds-lane wait, which returns as soon as a lane finishes, blocks, or dies, with a 30-minute cron as a backstop, rather than asking a model to judge whether a lane looks stuck.

Similar designs elsewhere

DeepSeek published dsh-superagent-prototype, a research prototype built for DeepSeek Harness, on October 31, and AI LABS rebuilt the idea in Claude Code on November 5: a router agent that only dispatches, with workers in their own contexts. The prototype's README says it was adapted from DeepSeek's internal version and from the article Exploring Super-agent Design: Towards a More Autonomous Agent System, so the dates below are public release dates, not dates of origin. DinoStack's conductor shipped on September 29 (PR #954) and ds-lane on October 12 (PR #994), with Codex lanes following on October 14 (PR #1019). The Ecosystem Comparison sets the two designs side by side.
